# Release Docs

Draft the four release artifacts a release needs, grounded in what actually changed
since the previous release, and write them to `.tmp_release_docs/` so the release
tooling can pick them up.

## Inputs

This skill takes its inputs from the user's request and the surrounding conversation —
there is no separate prompt or confirmation step, and you should never block waiting for
input. Look for:

- **Target version** (optional): an explicit version such as `2.1.0` / `v2.1.0`, or a bump
  level like `patch` / `minor` / `major`. When invoked via the `/release-docs` command it
  arrives as the command argument. If none is given, infer the appropriate bump from the
  diff (see step 3) — do **not** stop to ask.
- **Extra guidance** (optional): anything the user adds — a change to emphasize, an intended
  audience/tone, or a specific previous tag to diff against. Honor it; otherwise fall back to
  the workflow defaults below.

If neither is provided, proceed with sensible defaults and still write all four drafts — the
user reviews and edits the files afterward (and the release tool also opens them in an editor
in interactive mode).

## The convention

Projects generated by (or modeled on) **generate-project** run `scripts/release.py`,
which looks for pre-written drafts in `.tmp_release_docs/`. For each artifact, if a
draft exists, is non-empty, and is newer than the previous release tag, the release
script uses it **verbatim** instead of generating that artifact. So each draft must be
a complete, ready-to-use document — not a sketch. Anything you omit, the release tool
either generates itself or (in non-interactive mode) ships as-is.

Write all four files even if some changes feel minor — consistency across them matters,
and a missing draft means the tool falls back to generated content (and prompts the user).

## The four files

| File | Purpose | Format |
|------|---------|--------|
| `.tmp_release_docs/commit.txt` | The **complete** release commit message | Plain text |
| `.tmp_release_docs/tag.txt` | The annotated git tag message (`git tag -a -m`) | Plain text |
| `.tmp_release_docs/changelog.md` | The new entry to prepend to `CHANGELOG.md` | Markdown |
| `.tmp_release_docs/release_notes.md` | The GitHub Release body | Markdown |

These are related but not identical. `commit.txt` and `tag.txt` are plain text for git;
`changelog.md` and `release_notes.md` are markdown for `CHANGELOG.md` and the GitHub
Release page. `release_notes.md` can build on `changelog.md` but should read as something
a user lands on from a release page — slightly more user-facing and self-contained.

## Workflow

### 1. Determine the previous release tag

Run the bundled helper from the repo root — it encapsulates the tag pattern and PEP 440
ordering and prints the git ranges to inspect. It lives in this skill's `scripts/` directory
(the skill's base directory is shown when the skill loads):

```bash
python <this-skill-dir>/scripts/find_previous_release.py
```

It matches release tags with this pattern (the same one `generate-project` uses):

```
^v\d+\.\d+\.\d+(?:[-.]?(?:a|alpha|b|beta|rc|dev|post)\d*)?$
```

It sorts matching tags by PEP 440 and reports the highest as the previous release. **If no
tag matches, treat the entire reachable history as unreleased** and inspect all of it. (If
you can't run the script, list tags with `git tag --list`, keep the ones matching the
pattern, and pick the highest version.)

The script uses the `packaging` library for exact PEP 440 ordering; if it isn't installed it
falls back to approximate ordering and prints a warning to stderr. If you see that warning,
double-check the selected previous tag (or install `packaging`) before trusting the diff.

### 2. Inspect the full diff since that tag — not just commit subjects

Commit subjects lie or omit; read the real changes. Over the range the helper printed
(`<previous_tag>..HEAD`, or full history if there's no tag):

```bash
git log <previous_tag>..HEAD
git diff --stat <previous_tag>..HEAD     # the map: which files/areas changed
git diff <previous_tag>..HEAD            # the substance: read enough to understand it
```

(With no previous tag: `git log`, `git diff --stat <empty-tree> HEAD`, `git diff <empty-tree> HEAD` — the helper prints the exact empty-tree command.)

Read enough of the actual diff to understand **what changed and why it matters to a user**:
new/changed CLI flags or APIs, behavior changes, bug fixes, removals, config/packaging
changes (dependencies, build backend, minimum versions), CI/workflow changes, and docs.
`--stat` tells you where to look; open the meaningful hunks. Don't infer impact you can't
see in the diff.

### 3. Decide the version and categorize the changes

Determine the new version: use the version the user gave you; otherwise infer the semantic
bump from the diff (breaking changes → major, new features → minor, fixes only → patch) and
apply it to the previous tag. Use today's date (`YYYY-MM-DD`) for dated entries.

Group changes by the categories that are actually present (omit empty ones): **Breaking
Changes**, **Added**, **Changed**, **Deprecated**, **Removed**, **Fixed**, **Security**,
**Documentation**, **Internal**. Lead with user-visible behavior; put internal/refactor
details last or under **Internal**.

### 4. Write the four files

Create `.tmp_release_docs/` if needed and write all four files directly, **overwriting any
existing drafts** — when the user asks to prepare release docs, stale drafts should be
replaced. Do not ask for confirmation before writing.

## File formats

### commit.txt — the complete commit message

Plain text. This is the *entire* message (header + body), because the release tool uses it
verbatim — it does not add a header for you. Structure:

```
release <version>: <type>(<scope>) <optional short summary>

Changes
--------------------------------------------------------------------------------
- <concise, user-facing change>
- <concise, user-facing change>
- ...
```

- Header: `release <version>: <type>(<scope>)`. `<type>` follows the bump — `fix` for a
  patch, `feat` for minor/major (append `!`, e.g. `feat(major)!`, when there are breaking
  changes); `<scope>` is the bump level (`patch`/`minor`/`major`) for generate-project-style
  repos, or a sensible scope otherwise. If the exact new version isn't settled, use your best
  determination from step 3 — the release tool opens the message in an editor for review.
- Then a blank line, the literal word `Changes`, and a separator line of dashes
  (generate-project uses 80).
- Then concise bullets of the real, user-facing changes. Group with short headings if there
  are many distinct categories.

### tag.txt — the annotated tag message

Plain text, concise and durable (people read it years later via `git show <tag>`):

```
Release v<version> — <YYYY-MM-DD>

- <highlight>
- <highlight>
```

A short title line plus a few bullets of the headline changes. No markdown syntax that
would look odd in `git show` (plain hyphen bullets are fine). Keep it tight — this is a
summary, not the full changelog.

### changelog.md — the CHANGELOG entry

Markdown, scoped to this release only (the release tool prepends it to `CHANGELOG.md`). Use
Keep a Changelog-style headings, matching generate-project's `## [version] - date` format:

```markdown
## [<version>] - <YYYY-MM-DD>

### Added
- ...

### Changed
- ...

### Fixed
- ...
```

Include only the categories that apply. Call out breaking changes prominently (a
`### Breaking Changes` section and/or migration notes).

### release_notes.md — the GitHub Release body

Markdown, suitable for the GitHub Release page. Start from the changelog content but make it
read well standalone and a touch more user-facing: a one- or two-line summary of the release
up top is welcome, then the grouped highlights. Include upgrade/migration guidance when there
are breaking changes. Avoid repo-internal noise that doesn't help a reader of the release.

## Best practices

- **Be accurate and specific** — describe what the diff actually shows; never overclaim
  impact you can't see in the changes.
- **Group by user-relevant categories** (Added / Changed / Fixed / Removed / Deprecated /
  Security / Documentation / Internal / Breaking Changes) when it aids scanning.
- **Surface breaking changes loudly**, with clear migration/upgrade notes.
- **User-visible behavior before internal detail** — what changed for someone using the
  project comes first; refactors and tooling come last (or under Internal).
- **Don't paste raw commit logs** unless they're already clear and user-facing.
- **Prefer concise bullets** over long prose; add a sentence of explanation only where a
  change genuinely needs it.
- **Keep `tag.txt` concise and plain text**; keep `release_notes.md` shaped for a GitHub
  Release body.
- **Keep all four files internally consistent** — same version, same date, same set of
  changes described at the right altitude for each medium.

## Notes

- This skill only writes drafts; it never tags, commits, or publishes. The release tool
  (e.g. `scripts/release.py` / `make release-*`) consumes them later.
- `.tmp_release_docs/` is git-ignored in generate-project repos; if it isn't ignored in the
  target repo, mention that to the user rather than committing the drafts.
- The drafts must be newer than the previous release tag to be picked up, so writing them
  fresh right before a release is exactly right.
